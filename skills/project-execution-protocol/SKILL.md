# Project Execution Protocol

Этот skill задаёт рабочий протокол для реальных задач в репозитории.
Фокус: корректность изменений, целостность проекта и экономное использование контекста.

Skill не заменяет локальные правила проекта (например, `AGENTS.md`), а помогает исполнять их последовательно.

## Когда использовать

Используй skill, когда нужно:

1. Вносить изменения с жёстким контролем scope.
2. Делать минимальные и безопасные правки без лишнего рефакторинга.
3. Разделять работу по типам (реализация, отладка, исследование, документация).
4. Снижать риск регрессий через поэтапную верификацию.
5. Держать короткие, практичные пользовательские отчёты на русском языке.

## Когда не стоит вызывать

Обычно не нужен для разовых простых запросов, где нет редактирования кода, сложной проверки или риска расширения scope.

## Принципы

1. Держи узкий scope по умолчанию.
2. Расширяй контекст только при нехватке фактов.
3. Предпочитай минимальный безопасный diff.
4. Сохраняй архитектуру, нейминг и паттерны проекта.
5. Не смешивай несвязанные цели в одном проходе без явного запроса.

## Рабочий протокол

### Шаг 1: Intake Card

Перед изменениями зафиксируй:

- задачу,
- цель,
- границы scope,
- ограничения,
- релевантные файлы,
- неизвестные,
- минимальный следующий шаг.

### Шаг 2: Лестница контекста

Расширяй анализ по уровням:

1. Прямой файл или модуль.
2. Соседние зависимости (imports/helpers/consumers).
3. Связанный поток вызовов и wiring.
4. Широкий поиск только если уровни 1–3 недостаточны.

### Шаг 3: Правила исполнения

1. Делай наименьшее корректное изменение.
2. Не меняй публичное поведение без явной необходимости.
3. Избегай «попутной уборки» вне задачи.
4. Не меняй структуру модулей без причины.
5. Эскалируй важные изменения контрактов и интеграций перед реализацией.

### Шаг 4: Верификация

Проверяй от меньшего к большему:

1. Затронутые тесты.
2. Связанные интеграционные/e2e проверки.
3. Линт и typecheck для затронутой поверхности.

Если проверка не выполнена, явно укажи что именно не запускалось и почему.

### Шаг 5: Формат результата

Отчёт должен быть коротким и практичным:

- что проанализировано,
- что изменено,
- риски/блокеры/открытые вопросы,
- что проверить следующим шагом.

## Гигиена треда

Если тред смешивает разные цели и теряет фокус, предложи новый тред и укажи:

1. краткую причину,
2. заголовок,
3. стартовый промпт.

## Быстрый шаблон вызова

```text
Use project-execution-protocol.
Read: CURRENT_STATUS.md, <relevant files>
Task: <single concrete task>
Scope: <specific area only>
Constraints: minimal patch, no unrelated changes
Need: implement/fix + concise Russian summary + what to test
```
